# Кластер ключ/значение на Raft

[![CI](https://github.com/RishatShay/sna-final-project/actions/workflows/ci.yml/badge.svg)](https://github.com/RishatShay/sna-final-project/actions/workflows/ci.yml)

Это реализация Raft, алгоритма консенсуса, который позволяет кластеру узлов договориться
об одном лидере и держать реплицированный лог синхронным, даже если узлы падают или сеть
ведёт себя плохо. У такого кластера нет единой точки отказа: если лидер умирает, оставшиеся
узлы выбирают нового и кластер продолжает принимать записи. На этой же идее построены
реальные системы: etcd (а через него и Kubernetes), Consul и CockroachDB используют Raft
внутри именно по этой причине.

Здесь на нём построено реплицированное хранилище ключ/значение из пяти узлов, написанное
на Go с нуля: выборы лидера, репликация лога, снапшоты и надёжная машина состояний на
SQLite. Узлы общаются между собой по gRPC, и тот же gRPC служит клиентским API.

Это не поделка на коленке, которая работает только в идеальных условиях. Отставший
последователь догоняет кластер одним из двух способов: лидер либо досылает недостающие
записи лога, либо, если они уже были компактизированы, отправляет целый снапшот. Оба пути
покрыты интеграционными тестами вместе с переизбранием лидера и восстановлением после сбоя.

В репозитории есть и мониторинг, чтобы за консенсусом можно было реально наблюдать:
метрики Prometheus на каждом узле, JSON логи, которые Promtail отправляет в Loki, и
дашборд Grafana с алертами на «нет лидера» и «потерян кворум».

English version: [../README.md](../README.md).

## Что реализовано

- Выборы лидера со случайным таймаутом, `currentTerm` и `votedFor` сохраняются на диск.
- Репликация лога с проверкой согласованности в `AppendEntries`, обрезкой конфликтующих
  записей и откатом `nextIndex` для отставших узлов.
- Ответ на запись приходит только после того, как большинство узлов сохранило запись на диск.
- Компактизация лога: применённые записи заменяются снапшотом, а слишком отставший
  последователь восстанавливается через `InstallSnapshot`.
- Чтения обслуживает лидер, но только после раунда heartbeat, который подтверждает, что у
  лидера всё ещё есть большинство. Так лидер, отрезанный от кластера, не отдаст устаревшие
  данные.
- Клиентские запросы принимает любой узел: последователь перенаправляет их лидеру, о котором
  знает.
- `raftctl compare` проверяет, что у всех узлов одинаковый закоммиченный лог.
- Метрики Prometheus, JSON логи, дашборд и правила алертов Grafana.

## Быстрый старт

Нужен Docker с Compose v2 и больше ничего: сборка идёт внутри образа.

```bash
docker compose up --build -d     # пять узлов плюс Prometheus, Loki, Grafana
./scripts/demo.sh status         # кто сейчас лидер
```

Запись и чтение ключа. Работает через любой узел, последователи перенаправляют запрос лидеру:

```bash
docker compose exec node3 raftctl -addr node3:9001 write course sna
docker compose exec node1 raftctl -addr node1:9001 read course
```

Проверить, что лог одинаковый на всех узлах:

```bash
docker compose exec node1 raftctl -addr node1:9001 compare \
  node1:9001 node2:9001 node3:9001 node4:9001 node5:9001
```

С хоста узлы доступны на `localhost:9001` ... `localhost:9005`, поэтому работает и
`go run ./cmd/raftctl`:

```bash
go run ./cmd/raftctl -addr localhost:9002 write topic consensus
go run ./cmd/raftctl -addr localhost:9002 status
go run ./cmd/raftctl compare
```

| Сервис | Адрес |
| --- | --- |
| Grafana | <http://localhost:3000> (admin / admin) |
| Prometheus | <http://localhost:9090> |
| Loki | <http://localhost:3100> |
| Метрики и healthcheck узлов | <http://localhost:8001/metrics>, `/healthz`, порты 8001 ... 8005 |

`./scripts/demo.sh` показывает и интересные сценарии отказов: `failover` останавливает
лидера, `crash` перезапускает отставший узел, `quorum-loss` гасит три узла и показывает, что
записи отклоняются, `restore` возвращает всё на место. Подробности в
[operations.md](operations.md).

## Конфигурация

Узел читает конфигурацию из переменных окружения. Значения по умолчанию поднимают рабочий
кластер из одного узла прямо из корня репозитория.

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `NODE_ID` | `node1` | Постоянный идентификатор узла, используется в логах, метриках и голосовании. |
| `RAFT_GRPC_ADDR` | `:9001` | Адрес gRPC. |
| `RAFT_HTTP_ADDR` | `:8001` | Адрес, на котором отдаются `/metrics` и `/healthz`. |
| `RAFT_DATA_DIR` | `data/node1` | Каталог с файлом `raft.db`. |
| `RAFT_PEERS` | пусто | Список `id=host:port` через запятую. Может включать сам узел. |
| `RAFT_ELECTION_MIN_MS` | `500` | Нижняя граница таймаута выборов. |
| `RAFT_ELECTION_MAX_MS` | `900` | Верхняя граница таймаута выборов. |
| `RAFT_HEARTBEAT_MS` | `100` | Интервал heartbeat лидера. |
| `RAFT_SNAPSHOT_THRESHOLD` | `10000` | Сколько применённых записей проходит между снапшотами. |
| `RAFT_LOG_LEVEL` | `info` | `debug`, `info`, `warn` или `error`. |

Некорректные значения приводят к ошибке при старте, а не тихо заменяются значением по
умолчанию. Например, таймаут выборов короче интервала heartbeat.

## Разработка

```bash
make test     # юнит и интеграционные тесты, кластер из трёх узлов поднимается в процессе
make race     # то же самое с детектором гонок
make vet
make build    # bin/raftnode и bin/raftctl
```

Сгенерированный код gRPC лежит в репозитории, поэтому для обычной сборки `protoc` не нужен.
После изменения proto файла:

```bash
make proto-tools   # один раз, ставит protoc-gen-go и protoc-gen-go-grpc
make proto
```

CI проверяет форматирование, go vet, тесты и детектор гонок, а также то, что закоммиченный
сгенерированный код соответствует `raft.proto`.

Драйвер SQLite это [modernc.org/sqlite](https://modernc.org/sqlite), чистая реализация на Go,
поэтому бинари статические, а образу не нужен компилятор C.

## Ограничения

Это учебная реализация, специально небольшая. Она не заменяет etcd или Consul.

- Состав кластера фиксируется при запуске, изменения конфигурации через joint consensus нет.
- Новый лидер не коммитит пустую запись, поэтому записи из предыдущих термов коммитятся
  только вместе с первой записью текущего терма.
- В машине состояний две команды, `set` и `delete`, со строковыми ключами и значениями.
- Нет TLS и аутентификации: обычный gRPC в доверенной сети.
- Запись не дедуплицируется: повторно отправленный запрос может примениться дважды.

Изначально это был командный университетский проект. Здесь лежит переработанная версия: две
реализации, которые сделала команда, объединены в одну, сгенерированный код gRPC настоящий, а
не написанный руками, а код консенсуса, тесты, мониторинг и документация переписаны.
